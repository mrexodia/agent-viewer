1. Building a Mental Model

Before diving into code, let's establish an intuitive understanding of what this system does and why it exists.

🧠 Think of it like a Security Camera System

📹 Security Camera System

Cameras watch areas → Feed goes to security room → Monitors display live feeds

🤖 Agent Viewer System

Watcher monitors files → Server receives events → Browser displays live updates

📁 JSONL files (logs of agent activity) → Like camera footage being recorded
👀 Watcher (fsnotify + websocket) → Like cameras sending feeds to control room
🖥️ Server (receives + broadcasts) → Like the security control room
🌐 Browser (SSE + display) → Like monitors showing live feeds

💡 Key Insight: Event Streaming

This is an event streaming system. Instead of the browser asking "any updates?" repeatedly (polling), the server pushes updates as they happen. This is why it's real-time with <500ms latency.

The Core Problem Being Solved

When an AI agent runs (like Claude doing a task), it writes its activity to log files. You want to:

  • See what the agent is thinking/doing as it happens
  • Monitor multiple agents at once
  • Open a browser and just watch — no setup

The challenge: files are on disk, browsers can't read local files, and you want instant updates.

Watcher (watcher/main.go)

Job: Monitor a directory for .jsonl files and stream any new lines to the server.

How:
  • fsnotify library detects file changes
  • Reads only NEW lines (tracks position per file)
  • Batches lines every 100ms (efficiency)

Server (server/main.go)

Job: Receive lines from watcher, store in memory, broadcast to browsers.

Key structures:
  • SessionStore — Map of path → session data
  • SSEBroadcaster — Manages connected browser clients
Endpoints:
  • GET / — Serve the web UI
  • GET /api/sessions — List all sessions
  • GET /api/sessions/{path}/stream — SSE stream
  • WS /watch — Watcher connects here
Browser (server/static/index.html)

Job: Display sessions with live updates in a nice UI.

Key features:
  • Session list with live indicators (green dot = active)
  • Two views: "Pretty" (parsed JSON) and "Raw" (lines)
  • Auto-scroll that disables when you scroll up
  • Uses EventSource API for Server-Sent Events

🔧 Why Two Protocols?

WebSocket (Watcher → Server): Bidirectional, good for the watcher sending lots of data. Could add handshakes later.

SSE (Server → Browser): Simple, HTTP-based, browsers handle reconnection automatically. Perfect for server-to-client push.

💡 The Magic of fsnotify

The watcher doesn't poll files — it uses OS-level file system notifications. On Linux this is inotify, on macOS it's FSEvents. The fsnotify library abstracts these differences.

How the Watcher Reads Files (watcher/main.go)

The watcher tracks which lines it has already sent, and only reads new ones:

// FileState tracks the read position of a file
type FileState struct {
    Path     string // Relative path from watch root
    LastLine int    // Last line number sent
    LastSize int64  // Last known file size
}

// readFile reads all lines and queues only NEW ones
func (w *Watcher) readFile(absPath, relPath string) error {
    file, err := os.Open(absPath)
    // ...
    
    reader := bufio.NewReader(file)
    lineNum := 0
    
    for {
        line, err := reader.ReadString('\n')
        lineNum++
        
        // Skip lines we've already sent
        if lineNum <= state.LastLine {
            continue
        }
        
        // Queue for sending
        w.lineQueue <- LineMessage{
            Type: "line",
            Path: relPath,
            Line: line,
        }
    }
}

Key insight: Uses bufio.NewReader instead of bufio.Scanner because Scanner has a max token size (64KB), but agent logs can have huge lines (think: base64 images).

Batching for Efficiency (watcher/main.go)

Instead of sending every line immediately, the watcher batches them:

// batchSender collects lines and sends them in batches
func (w *Watcher) batchSender() {
    ticker := time.NewTicker(time.Duration(w.batchMs) * time.Millisecond)
    defer ticker.Stop()

    var batch []LineMessage

    for {
        select {
        case msg := <-w.lineQueue:
            // Accumulate lines
            batch = append(batch, msg)
            
        case <-ticker.C:
            // Every 100ms, send whatever we've accumulated
            if len(batch) > 0 {
                for _, msg := range batch {
                    w.sendLine(msg)
                }
                batch = batch[:0] // Clear
            }
        }
    }
}

Why batch? An agent might write 50 lines in quick succession. Sending 1 message with 50 lines is more efficient than 50 separate WebSocket frames.

Broadcasting to Subscribers (server/main.go)

When the server receives a line, it broadcasts to all interested SSE clients:

// Broadcast sends an event to all clients watching a path
func (b *SSEBroadcaster) Broadcast(event LineEvent) {
    b.mu.RLock()
    defer b.mu.RUnlock()

    for client := range b.clients {
        // Send to clients watching this specific path or all paths
        if client.path == "" || client.path == event.Path {
            // Block until we can send - never drop events
            client.events <- event
        }
    }
}

Design choice: The broadcast blocks if a client's buffer is full. This guarantees no data loss (MVP priority) but could cause slowdown with very slow clients. Future: add timeout or drop slow clients.

SSE Streaming to Browsers (server/main.go)

Server-Sent Events use a specific text format:

func (s *Server) handleSessionStream(w http.ResponseWriter, ...) {
    // SSE requires these headers
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")

    // Get the Flusher to push data immediately
    flusher, _ := w.(http.Flusher)

    // First, send all existing lines
    session := s.store.GetSession(path)
    for i, line := range session.Lines {
        fmt.Fprintf(w, "event: line\ndata: %s\n\n", data)
    }
    flusher.Flush()

    // Then stream new events as they arrive
    for {
        select {
        case event := <-client.events:
            fmt.Fprintf(w, "event: line\ndata: %s\n\n", data)
            flusher.Flush()
        case <-r.Context().Done():
            return // Client disconnected
        }
    }
}

SSE format: Each event is event: name\ndata: payload\n\n. The double newline marks end of event. Browsers handle reconnection automatically!

⚠️ Concurrency Note

The server uses sync.RWMutex for thread safety. Multiple browser clients can READ sessions concurrently (RLock), but writes from the watcher need exclusive access (Lock). This is why you see mu.RLock() vs mu.Lock() in the code.

5. Edge Cases & Error Handling

Robust systems handle the unexpected. Here's how Agent Viewer deals with edge cases:

File Truncation

What if a file gets replaced (e.g., log rotation)?

// In readFile():
if info.Size() < state.LastSize {
    log.Printf("File %s was truncated, resending all lines", relPath)
    state.LastLine = 0
    state.LastSize = 0
}

Connection Loss

The watcher implements exponential backoff reconnection:

func (w *Watcher) Reconnect() {
    backoff := time.Second
    maxBackoff := 30 * time.Second

    for {
        log.Printf("Reconnecting in %v...", backoff)
        time.Sleep(backoff)

        if err := w.Connect(); err != nil {
            backoff *= 2  // 1s, 2s, 4s, 8s...
            if backoff > maxBackoff {
                backoff = maxBackoff
            }
        } else {
            return // Success!
        }
    }
}

Path Traversal Attack

Malicious path like ../../../etc/passwd?

// Server rejects ".." in paths
if strings.Contains(path, "..") {
    http.Error(w, "Invalid path", http.StatusBadRequest)
    return
}

Very Long Lines

Some agent logs include base64-encoded images (megabytes!). The integration tests verify 5MB+ lines work:

6. Check Your Understanding

1. Why does the watcher use WebSocket instead of SSE to send data to the server?
SSE only works in browsers, not in Go programs
WebSocket is bidirectional, allowing for future handshakes/acknowledgments
WebSocket is faster than SSE
There's no particular reason, they're equivalent
2. What happens if the server process restarts?
Data is restored from disk
All session data is lost (in-memory only for MVP)
The watcher replays from its checkpoint file
Browser clients restore data from their cache
3. Why does the broadcaster BLOCK when a client's buffer is full, rather than dropping events?
It's a bug that should be fixed
MVP prioritizes "no data loss" over performance with slow clients
Go channels can't drop messages
SSE requires in-order delivery with no gaps
4. How does the watcher handle a new subdirectory being created while it's running?
It doesn't — you need to restart the watcher
It uses inotify's IN_CREATE flag to detect new directories
addDirectoryRecursive() adds the new dir and scans for .jsonl files
It polls the directory tree every 5 seconds
5. Why use bufio.Reader instead of bufio.Scanner for reading lines?
Reader is faster than Scanner
Scanner has a max token size (64KB), but agent logs can have huge lines
Reader supports seeking, Scanner doesn't
Scanner doesn't handle UTF-8 correctly

7. Critique & Future Ideas

Now that you understand the system, you're equipped to critique it and think of improvements!

Known Limitations (Per the README)

  • No persistence — Restart = data loss
  • No auth — Localhost only
  • In-memory only — Large sessions consume RAM
  • No filtering — Shows all lines, no search

🤔 Questions to Ponder

Architecture Questions

  • Could the watcher and server be combined into one process? What are the tradeoffs?
  • Is WebSocket the right choice for watcher→server, or would gRPC/QUIC be better for high-volume streaming?
  • What if you wanted to support 1000 concurrent browser clients?

Reliability Questions

  • How would you add "exactly-once" delivery guarantees?
  • What if the watcher crashes mid-file? How would you implement checkpointing?
  • Should the server acknowledge received lines? What protocol would you use?

Feature Ideas

  • Session hierarchies (parent agent → subagents) — how would you model this?
  • Full-text search across all sessions — SQLite FTS? Elasticsearch?
  • Time-travel debugging — replay sessions at different speeds?
  • Collaborative viewing — see where other viewers are looking?
